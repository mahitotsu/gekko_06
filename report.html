検証レポート — Claude Agent SDK (TypeScript)

stdio MCPサーバーの寿命

uv run で起動したMCPサーバーの子プロセスを、Claude Agent SDKはいつ・どうやって終了させるのか。11パターンの実験とプロセスツリー観察、そしてMCP仕様・公式ドキュメントとの突き合わせで確かめた記録。

検証日 2026-09-01〜02 @anthropic-ai/claude-agent-sdk 0.3.252 同梱CLI 2.1.252 mcp (Python) 1.29.1 uv 0.9.18

MCPサーバーをstdio(標準入出力)でつなぐと、クライアント側がサブプロセスとして起動する。ではセッションが終わったあと、その子プロセスは誰が、どう片付けるのか。放置してゾンビ化しないのか、行儀の悪いサーバーだったら、親プロセス自体が突然死んだら——公式ドキュメントには書かれていないこの領域を、11パターンの実験とプロセスツリー観察で確かめた。

先に結論

正常系(A〜G)
正常終了・中断・サブエージェント・逐次/並列セッション、すべて1〜2秒で子プロセスは自動的に消える。後始末コードは不要。
行儀の悪いサーバー(E, F)
シグナルを無視してもstdin EOFで自然終了。それも無視する最強に強情な相手には、約5.8秒後にSIGKILL。
CLIプロセスを直接kill(H, I)
uv自体が独立した安全装置になっていて、約1秒で子(MCPサーバー)を道連れに自滅する。
Node.jsホスト自体がクラッシュ(J, K)
この安全装置は働かない。CLIプロセスは最大60秒観察しても自己終了せず、確実に孤児として残る。唯一の本物のリーク源。

前提知識:誰が何を呼んでいるのか

この先「CLI」「セッション」といった言葉が説明なしに出てくる。まずClaude Agent SDKが裏で何をしているかを押さえておく。

query()を呼んでも、自分のNode.jsコードが全部やっているわけではない。SDKは裏で別プロセスとしてclaudeコマンド本体を起動し、標準入出力でJSONメッセージをやり取りする薄いラッパーにすぎない。今回のようにMCPサーバーをstdioで繋ぐと、プロセスはさらにもう二段深くなる。

① あなたのNode.jsスクリプト — 自分で書いたコード。query()を呼ぶだけの薄いラッパー
└─ ② claude CLIプロセス — SDKが裏で起動する claude コマンド本体。以後「CLI」と呼ぶ
└─ ③ uv run main.py — CLIがMCPサーバーを起動するために使うランチャー
└─ ④ python3 main.py — MCPサーバー本体(今回検証した対象)

API通信・ツールの実行判断・MCPサーバーとの接続管理をしているのは、実は①ではなく②のCLIだ。①が消えても②は自動的には消えない——これが後半の「親が死んだら」の章の伏線になる。

この記事で使う言葉

query()
SDKが提供する関数。プロンプトを渡すとメッセージのストリームが返る。呼ぶたびに新しいCLIプロセスが1つ起動される。
セッション
1回のquery()呼び出しに対応する、CLI⇔MCPサーバー間の一連のやり取り。stdio transportでは「1セッション = 1プロセス」が仕様上の必然(後述)。
CLI
SDKが裏で起動するclaudeコマンド本体(上図②)。ターミナルで直接打つclaudeコマンドと同じ実行ファイル。
stdio transport
MCPサーバーとの通信方式の一つ。クライアント(CLI)がサーバーをサブプロセスとして起動し、標準入出力でJSON-RPCをやり取りする。
MCPサーバー
ツールを提供する外部プロセス(上図④)。今回はPythonの最小FastMCPサーバーをuv runで起動した。
サブエージェント
同じセッション内で、別のシステムプロンプト・ツールセットを持つ「子」のやり取り。Taskツール経由で呼ばれるが、別プロセスにはならない。
SIGINT/SIGTERM
プロセスへ送る終了シグナル。プロセス側でハンドラを登録して捕捉・無視できる。
SIGKILL
強制終了シグナル。カーネルレベルで強制され、プロセス側は捕捉も無視もできない唯一の手段。
孤児プロセス
親プロセスが死んだ後も生き残った子プロセス。init(PID 1)の下に付け替えられ、誰も後始末しなければ動き続ける。

実験の骨組み

最小のFastMCPサーバー(Python、uv runで起動)を1つ用意した。ツールは即応するechoと、指定秒数sleepしてから返すslow_echoの2つだけ。起動直後に自分のPIDをファイルへ書き出し、ログはすべてstderrに逃がしてJSON-RPCの邪魔をしないようにしている。

TypeScript側は@anthropic-ai/claude-agent-sdkのquery()にこのサーバーをmcpServersとして登録し、allowedToolsで該当ツールだけを許可、disallowedToolsでBashなど他の手段を封じて「MCP経由でしか目的を達成できない」状況を作った。プロセスの生死は外側からkill -0で0.2秒間隔にポーリングし、スクリプト終了後も30秒間追跡している。

B 中断(interrupt)

サブエージェントがMCPツールの結果を受け取り、報告をまとめ終えたあとも、サーバーはおよそ2.5秒生き続けた。死ぬのはサブエージェントの完了ではなく、トップレベルのquery()セッションそのものが終わる瞬間だった。

共通パターン

A・B・Cいずれも、サーバーに直接シグナルハンドラを仕込んで実測すると、SIGINTとSIGTERMが1ミリ秒未満の差でほぼ同時に届いていた。SIGKILLは一度も観測されず、サーバー側はSIGTERMを受けた時点のPythonの後始末(anyio/FastMCPのタスクグループの終了処理など)だけでおよそ0.7〜1.0秒かけて自発的に終了している。

寄り道:「stdinクローズ」という推測は間違っていた

最初のドラフトでは、終了メカニズムを「stdinクローズによるサーバー側の自発終了」だろうと推測だけで書いていた。指摘を受けて確認すると、これは検証していない当てずっぽうだった。

そこでサーバー本体にシグナルハンドラと、SDK側からは見えない独立のログファイルを仕込み、実際に何が届いたのかを記録し直した。

$ cat run/server-shutdown-cause.log 2026-09-01T14:15:35.261305+00:00 pid=136409 STARTED 2026-09-01T14:15:40.978714+00:00 pid=136409 SIGNAL_RECEIVED signal=SIGINT(2) 2026-09-01T14:15:40.979282+00:00 pid=136409 SIGNAL_RECEIVED signal=SIGTERM(15) 2026-09-01T14:15:41.680239+00:00 pid=136409 SYSTEM_EXIT code=130 2026-09-01T14:15:41.680331+00:00 pid=136409 PROCESS_EXITING

stdinのEOFによる自然なreturn(スモークテストで</dev/nullを渡した時にだけ観測できた挙動)は、SDK経由の実行では一度も起きなかった。3パターンとも一貫して同じ結果——SIGKILLまで頼らずに済む、素早いシグナルによる強制終了だった。

誰が誰を殺しているのか — プロセスツリーを見る

信号が届く経路を確かめるため、slow_echoで15秒間サーバーを稼働させたままps --forestで親子関係を観察した。

claude — CLI本体(実体は claude-agent-sdk-linux-x64/claude、214MBの単一実行バイナリ)
└─ uv run --directory pyserver main.py — claudeの直接の子
└─ python3 main.py — MCPサーバー本体。uvはexecで自身を置き換えていない

重要なのは、このとき検証スクリプト自身(Node/tsxとその祖先プロセス群)は同じプロセスグループに属していながら、シグナルの影響を一切受けず動き続けていたことだ。つまりプロセスグループ全体への一斉kill(-pgid)ではない。もっとも筋が通る説明は、claudeが直接の子であるuvだけを狙ってkillし、uvがそれを孫のpython3へ中継(フォワード)している、というものだ。

ここは推論どまり

claudeバイナリは214MBのコンパイル済み単一実行ファイルで、現実的に逆解析できなかった。kill()が具体的にどのAPI・引数で呼ばれているかのソースレベルの確認はできていない。プロセスツリーという状況証拠からの推論として報告する。

Pattern D — メインプロセスを生かしたまま、2回query()する

「MCPサーバーはquery()単位(セッション)に紐づくのか、それともNode.jsのメインプロセスに紐づくのか」を切り分けるため、同一のメインプロセス内でquery()を2回連続実行した。メインプロセス自体は一度も終了させていない。

メインNode.jsプロセス pid = 138606 — 2回のquery()の間、ずっと生存
query() 1回目
server pid 138684
完了直後にはすでに死亡
query() 2回目
server pid 138797
1回目とは別プロセスとして起動

メインNode.jsプロセスは2回のquery()の間ずっと生き続けたにもかかわらず、MCPサーバーは1回目と2回目で別PIDになった。MCPサーバーのライフサイクルは、メインプロセスの生存期間ではなく、個々のquery()呼び出し(実質的にMCPの1セッション)に紐づく。

Pattern G — 同時に2つ動かしたら?

ついでに、同じメインプロセスからquery()を同時に(並列で)2つ実行してみた。共有ロックのようなものは働くのか、それとも単純に2プロセス立つのか。

メインNode.jsプロセス pid = 142276 — 2つのセッションを同時発火
session-1 (slow_echo 8秒)
server pid 142402
+2秒後も生存 → 独立して完了・終了
session-2 (slow_echo 8秒)
server pid 142396
+2秒後も生存 → 独立して完了・終了

2つのサーバーが同時刻に生存していることを確認した上で、それぞれ独立して(共有もロック待ちもなく)完了・終了した。並列実行しても振る舞いはPattern Dの延長線上——「1 query() = 1 MCPサーバープロセス」が並列度に関わらず保たれる。

もし行儀の悪いMCPサーバーだったら

ここまでは全部、シグナルに素直に応答するサーバーだった。ではシグナルを無視するサーバーだったらどうなるか。最終的には強制終了(SIGKILL)されるのか、それとも居座り続けるのか。

E シグナルだけ無視する

SIGTERM/SIGINT/SIGHUPすべてを握りつぶすハンドラを仕込んだサーバー。

stdin EOFで自然終了(SIGKILL不要)
$ cat run/server-shutdown-cause.log ...STARTED ...SIGNAL_RECEIVED_BUT_IGNORED signal=SIGINT(2) ...SIGNAL_RECEIVED_BUT_IGNORED signal=SIGTERM(15) ...MCP_RUN_RETURNED_NATURALLY ← 約0.3秒後、シグナルを無視したのに自然終了

CLIはシグナル送信と並行してstdinのクローズも行っているらしく、MCP Python SDKの内部読み取りループがEOFを検知して自発的に抜けた。仕様どおりの経路がちゃんと機能していた。

F シグナル+stdin EOFの両方を無視する(最強に強情)

シグナルを無視するだけでなく、mcp.run()が自然リターンしても無限ループで再突入し続け、居座り続けようとするサーバー。

約5.8秒後にSIGKILLで強制終了
SIGINT/SIGTERM
(無視される)
最後のループログ
(loop=6)
無音のまま消滅
+5.80秒

サーバー自身のログはEXCEPTION_SUPPRESSED type=ValueErrorを1秒おきに6回記録したあと、何の前触れもなく途切れた。ログに何も残せないまま消える、というのがSIGKILL(捕捉不能)の状態証拠そのものだ。

SIGKILLは実在した

CLIは、シグナルを無視するだけの相手にはstdin EOFという第二の手段で対応し、それすら無視する本当に強情な相手には、約5.8秒の猶予を与えたのち有無を言わさずSIGKILLしていた。SIGKILLはカーネルレベルで強制されるシグナルで、ハンドラの登録・無視・ブロックが一切できない——プロセス側に打つ手はない。

親が死んだら、子はどうなるか

ここまでの実験は全部、親(CLI)が生きたまま自発的に子を後始末するケースだった。では親自体が——たとえばホストプロセスがクラッシュして——後始末する間もなく突然死んだらどうなるのか。これは読者からの指摘で気づいた、本質的に別の問いだった。

CLIプロセスを直接killする(H, I)

外部からclaude CLIプロセスへkill -9を撃ち込み、通常サーバー(H)と最強に強情なサーバー(I)それぞれの生死を追った。

claude ← 外部から kill -9
└─ uv run ... ← 自分の入出力が壊れたのを検知し、子を道連れに自滅
└─ python3 main.py (通常・最強に強情、どちらも同じ結果)

結果は両方とも約1秒で終了——通常サーバー(H)は1.0秒、最強に強情なサーバー(I)ですら1.1秒だった。シグナルを無視するIのケースでは、サーバー自身のログにSIGNAL_RECEIVEDの記録が一切ない。それでも死んでいる。uv自身のPIDを追跡すると、uvとpython3がほぼ同時(0.3秒以内)に消滅していた。CLIが死ぬと、直接の子であるuvが自分の入出力の破損を検知して、子(MCPサーバー)を道連れに自滅している——uv run自体が、CLIとは独立したもう一段の安全装置として機能していた。

Node.jsホストプロセスそのものをkillする(J, K)

今度はCLIの親、つまりnpx tsx ...を実行しているNode.jsプロセス自体を外部からkill -9する。CLIより一段上を落とすだけなので、理屈上は同じ結果になりそうに思えたが——

Node.jsホストプロセス — 外部からkill -9(この後は存在しない)
通常サーバー(J / J2)
CLI: 25〜30秒生存
server: 12〜30秒でまちまち
タイミング次第で結果が変わる。保証された挙動ではない
最強に強情なサーバー(K)
CLI: 60秒経過後も生存
server: 51.8秒後に消滅
CLIは観測終了まで自己終了せず、手動killが必要だった

唯一一貫していたのは、claude CLIプロセス自体は、観測した範囲(最大60秒)では一度も自己終了しなかったということだ。MCPサーバー側は「CLIが自分の出力を書き込もうとして初めてパイプの破損に気づき、そのMCP接続だけ後始末する」というタイミング依存の経路で片付くことがある(J2では約12秒後、Kでは約51.8秒後)が、保証された挙動ではない——長時間ツールの実行中に親が死ねば(J)、その機会自体が来ないまま30秒経っても両方生き続けていた。

CLIを直接killする(H/I)のとは別物だった

uvという安全装置が効くのは、あくまでCLIの直接の子が異常を検知できる場合に限られる。Node.jsが死ぬと、CLIは(uvから見て)まだ生きている親であり続けるため、uvの安全装置は発動しない。CLI自身が気づくかどうかは、その瞬間に何をしていたか次第——これが今回見つかった唯一の、確実なプロセスリーク経路だった。

MCP公式仕様と比べるとどうか

MCP公式仕様(2025-06-18)のLifecycle章には、stdio transportのシャットダウン手順が明記されている。

仕様が推奨する手順(SHOULD)

  1. まずサーバーへのstdinを閉じる
  2. サーバーの終了を待つ。合理的な時間内に終了しなければSIGTERM
  3. SIGTERM後も終了しなければSIGKILL

実測されたClaude Code CLIの挙動

  1. stdinクローズは観測されず
  2. SIGINTとSIGTERMをほぼ同時(<1ms差)に送信。「様子見」の間は無い
  3. SIGKILLは一度も必要にならなかった

仕様の"SHOULD"(推奨であって必須ではない)からは外れているが、SIGTERMだけで毎回きれいに終了できている以上、実害のあるずれではなさそうだ。段階を踏まず即座に信号を送ることで、むしろ子プロセスの後始末を速くしている面もある。

セッションの単位はtransportで違う

同じ仕様のTransports章 Session Management節によれば、"session"の対応関係はtransportごとに設計が違う。

TransportセッションIDの概念プロセスとセッションの関係
stdio 存在しない 「1回のサブプロセス起動 = 1セッション」が構造的に固定。分離不可能
Streamable HTTP Mcp-Session-Idヘッダで明示 1つの長命プロセスが複数セッションを同時に処理できる。状態はセッションIDごとに分離する設計

今回のようにstdioでMCPサーバーを立てる構成では、「1 query() = 1 MCPサーバープロセス = 1セッション」が仕様上そもそも必然であり、Pattern Dの実測結果はこれと矛盾なく整合する。複数のquery()をまたいでサーバー側の状態を持たせたいなら、stdioではなくStreamable HTTPで長命サーバーを立て、セッションIDごとに状態を管理する設計に切り替える必要がある。

結局、何ができるようになったのか

この記事の一次的な価値は、Claude Agent SDKのドキュメントに明記されていない領域を、実際にプロセスを動かして確かめたということそのものにある。その上で、この挙動が実務上何を意味するのかを一言でまとめると——

TypeScriptで実装したagentは、uvで動くMCPサーバーを「プロセスがリークする心配なく」使える

ただし2つの条件つきだ。①MCPサーバー自身が(明示的に無視しない限り)シグナルかstdin EOFのどちらかに応答するという、MCP実装として最低限まっとうな作り方をしていること。②Node.jsホストプロセス自体が、クラッシュではなく正常な経路で終了すること。①は多少雑な実装でもuv run自身の安全装置(H/I)や最終手段のSIGKILL(F)がカバーしてくれる。問題は②で、ここだけはSDK側にもOS側にも自動的な安全網が存在しない。

  • 正常系の後始末を自分で書く必要はない。正常終了・中断・サブエージェント経由・逐次/並列セッションのいずれでも、query()セッションが終わればMCPサーバーの子プロセスは1〜2秒以内にSDK側が終了させる。
  • 多少行儀の悪いMCPサーバーでも、ほぼ大丈夫。シグナルを無視するだけならstdin EOFが、それも無視するならCLIの最終手段(約5.8秒後のSIGKILL)が、さらにCLI自体が消えてもuv run自身の安全装置(約1秒)が働く。3重の安全網があると言っていい。
  • 本当に気をつけるべきはただ1点、ホストプロセスのクラッシュ耐性。Node.jsプロセス自体がkill -9やOOM Killerなどで突然死すると、claude CLIプロセスは孤児として確実に残り、MCPサーバーもタイミング次第で残る。コンテナやsystemdなど、プロセスグループ単位で確実に後始末する仕組みを持つプロセス監督者の下で動かすことが唯一の対策になる。
  • 状態はセッション(=1回のquery())をまたいで残らない。stdio transportである以上、これは実装の都合ではなく仕様上の必然。複数ターンにまたがる状態を持たせたいなら、MCPサーバー自体をStreamable HTTPの長命プロセスとして設計し直す必要がある。
  • 公式ドキュメントは「粒度」までしか教えてくれない。「1 query() = 1 subprocess」という設計思想は文書化されているが、シグナルの種類・タイミング・異常系での挙動は今回のように自前のシグナルハンドラとプロセスツリー観察で確かめるほかなかった。
